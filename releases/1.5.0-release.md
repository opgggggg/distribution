# CubeOffice 1.5.0 · 发布复盘

2026-09-25 发布。四平台（macOS arm64 / Windows x64 / Linux x86_64 / Android）已上线
cubexp.com；鸿蒙候选包已构建签名，待提交华为审核。

源码身份：distribution `43cb8d9e8f293a2d684f961657c43ac4cc923705`，
upstream `490197d4681c6f6dfd4a9fe5cb8ab87cc1070735`。五个平台消费同一个提交。

版本号从 1.4.12 直接跳到 1.5.0，是发布时定的，不对应任何代码语义。

## 这一版有什么

桌面和安卓拿到的是 1.4.12 之后的 22 个上游提交：原生输入法归属与编辑交互回归修复、
Word 按字体计算行高与分节起始段前间距、跨页表格保持授权列宽、PDF 扫描件内嵌图片解码、
脚本叠加层预览失败回退原页面。

鸿蒙用户上一次拿到的是 1.4.7（1.4.8–1.4.12 没有出鸿蒙包），所以对他们而言这一版还包含
PC/2in1 的原生文档标签页（拖出成窗口、拖回合并、切换保留编辑状态）和放映切换幻灯片前
填充背景的修复——两者早在 1.4.8 之前就在 main 上，只是从未到达鸿蒙。AGC 的「新版本特性」
因此单独成文：[harmony-v1.5.0.md](harmony-v1.5.0.md)。

## 过程中踩到的坑

四次失败全部是环境缺口，没有一次是代码问题。

- **系统解析器解不出 cubexp.com**：当时生效的 DNS 来自 VPN 隧道上的内网解析器，它对
  `cubexp.com` 和 `www.cubexp.com` 都解析失败，而公共 DNS 正常、按 IP 直连站点也正常。
  `check-new` 第一步读线上 feed 就失败。断开 VPN 后恢复。github 和 gitlab 不受影响，
  所以很容易误判成脚本问题。
- **main 的子模块指针悬空**：main 指向 upstream `2b586420`，那个提交只存在于本地发布
  工作树，从未推送，于是任何新克隆或发布工作树的 `submodule update` 都会
  `not our ref`。修法分两步：把它承载的原生菜单路由修复 cherry-pick 到 upstream master
  （`490197d4`，自带的回归测试在新 master 上通过）并推送，再把 main 的指针改指过去
  （`0b27d95`）。**根因是 1.4.8–1.4.12 五次发布都没有把发布分支合回 main**，main 因此
  停在 1.4.7 时代并带着一个不可达的指针；本次已按 `a78309e` 的先例合回。
- **宿主 CONNECT 代理未启动**：Windows 虚拟机没有外网路由，靠宿主机上的代理脚本访问
  registry（地址见 `scripts/release/README.md`）。它不会被发布脚本自动拉起，忘了跑
  Windows 预检就以 `ECONNREFUSED` 失败。
- **Windows 构建机磁盘再次见底**：C 盘只剩 0.04 GB，cargo 写 rmeta 报 `os error 112`。
  删掉 1.4.8（3.03 GB）和 1.4.12（1.50 GB）的构建树并清 Temp 后恢复到 4.24 GB，构建
  通过——仍然很紧，下次发布前建议先看空间。可回收的只有跨版本构建树，脚本按设计不会
  自己删它们。
