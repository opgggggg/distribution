# CubeOffice 1.5.1 · 发布复盘

2026-09-25 发布，与 1.5.0 同日。四平台（macOS arm64 / Windows x64 / Linux x86_64 /
Android）已上线 cubexp.com；鸿蒙候选包已构建签名，待提交华为审核。

源码身份：distribution `6e451aec2f3b3da02c01a754d971c98fa487d4b1`，
upstream `080955f8a01f822057380c2c61aec8345f4a13d7`。五个平台消费同一个提交。

## 这一版有什么

1.5.0 发布后上游又进了 15 个提交，本版取其中用户可感知的部分：Word 段落跨页时最后一行
不再留空、分页估算与渲染实际断行位置对齐、Ctrl+Shift+Space 插入的不间断空格在渲染时不被
拆到两行，以及 PDF 图片提取改用文档打开时所用的编解码目录。

鸿蒙用户仍停在 1.4.7——1.5.0 的候选包构建了但从未提交 AGC，所以
[harmony-v1.5.1.md](harmony-v1.5.1.md) 把 1.5.0 的原生文档标签页和放映背景修复一并写进
「新版本特性」。

## 过程中踩到的坑

### 宿主 CONNECT 代理有个真实的 bug

`~/cubexp.com/windows-connect-proxy.py` 把两个中继 socket 都设成非阻塞后，仍然用
`sendall` 发送。非阻塞 socket 上发送缓冲一满就抛 `BlockingIOError`（EAGAIN），处理线程
直接死掉，VM 侧表现为 `npm ci` 随机 `ECONNRESET`——**看起来完全像网络问题**，实际与网络
无关：同一时刻这台 Mac 直连 registry 拉 4 MB 的包只要 1.7 秒。

之所以到这一版才暴露：为腾磁盘把 VM 的 npm 缓存删了，全量下载几百 MB 必然写满发送缓冲。
排查时先试了降 npm 并发和加重试（`maxsockets 3`、`fetch-retries 8`，写在 VM 的
`C:\Users\ALS\.npmrc`），没用——重试兜不住传输中途的连接重置。

修法是把发送改成 `send` 循环加等待可写（`send_all()`），已提交到该脚本，原文件备份为
`.bak-20260925`。修好后 Windows 从装依赖到编译完成约 58 分钟，全程没有再出现重置。
遗留一处噪音：中继的 `recv` 侧遇到对端重置仍会打印 traceback，发生在传输结束的拆连接
阶段，不影响结果。

### Windows 构建机磁盘

1.5.0 的构建树在成功后被脚本自清，但可用空间反而从 4.24 GB 降到 3.1 GB，低于 4 GB 预检
门槛。这次回收的是 `C:/office-target-cache-055`（2.53 GB，9/23 起未动）、
`C:/office-compat`（0.4 GB）、cargo registry 与 npm 缓存，腾到 6.19 GB。
今天仍在被写的 `C:/office-target-cache`（2.26 GB）保留未动。
发布配置里 `WINDOWS_TARGET_CACHE` 为空，这两个 target-cache 目录不属于本条发布链路。

### DNS 又失败了一次

第一次 `check-new` 仍因 `cubexp.com` 解析失败而停。几分钟后解析器从 VPN 切回 en0 即恢复，
属于瞬时状态，构建未开始。详见 [1.5.0-release.md](1.5.0-release.md) 里的同一条。
